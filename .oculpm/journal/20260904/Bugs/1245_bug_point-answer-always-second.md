[x] 지목형 정답이 늘 2번이었다 (D128) — 사전 절반이 정답을 가운데 pick 에 두고 오답이 양옆을 집는다

사용자 요청 4 — 「4지선다 문제의 답이 항상 2번인것같음」. 어느 판인지 확실치 않다고 해서 셋(지목형·빈칸/의미형·T2 방향)을 다 쟀다.

## 발생 원인

**지목형이다.** 정답 번호는 셔플이 아니라 「4개 자리를 코드 순서로 세운 뒤 정답이 몇 번째인가」로 정해진다. 그런데

- 사전의 point 항목 26개 중 **13개가 정답을 가운데 `pick.2`** 에 둔다(`pick.1` 6개 · `pick.3` 7개). `a?.b` 처럼 왼쪽 값 · 기호 · 오른쪽 이름으로 잡히는 캡처라 가운데가 답인 것이 자연스럽다.
- 오답 1순위가 「사전 `diag` 가 있는 pick」이라(04 §1.1) 양옆 `pick.1`·`pick.3` 이 먼저 뽑힌다.

셋을 코드 순서로 세우면 정답은 **언제나 두 번째**다. `t0.test.ts` 의 골든이 그 값을 「목업과 같다」며 굳히고 있었다 — 테스트가 편향을 지키고 있었던 셈이다.

나머지 둘은 편향이 아니었다(실측):

- 빈칸·의미형 — 시드 셔플. 292장에서 `72 / 78 / 73 / 69`.
- T2 의존성 방향 — 답이 관계 그 자체(0=A가 B를 · 1=B가 A를 · 2=서로 · 3=무관)라 셔플할 것이 없다. 픽스처의 import 쌍 7건이 `4 / 3 / 0 / 0` 으로 한쪽에 몰리지 않는다. 표본이 작아 단정하지 않는다 — 큰 리포에서 다시 잴 값이다.

## 해결 방법

`t0-point.ts` 에 `spread()` — 순위대로 세운 오답 후보를 정답 기준 앞뒤로 가른 뒤 「앞에서 b개 · 뒤에서 3−b개」를 고르고, b 를 그 카드의 시드가 정한다. 번호는 그대로 코드 순서이므로 정답 번호가 곧 b 이고, 카드마다 흩어진다. 낼 수 있는 b 의 범위는 양쪽 후보 수가 정한다(`lo = max(0, 3−뒤)` ~ `hi = min(3, 앞)`).

보기를 섞는 길은 쓸 수 없다 — 번호가 곧 코드 위 위치이고 `← →` 이동 순서와 같아야 한다(04 §1.1). 그래서 섞는 것은 보기가 아니라 **어느 쪽에서 오답을 고르는가**다.

치르는 값: 한쪽 후보가 모자라면 순위가 낮은 오답이 들어온다. 목업 optchain 카드가 그 예다 — 오답 셋이 전부 정답 뒤에 서면서 `res.user`(진단 있는 pick)가 빠지고 `'손님'`(리터럴, 4순위)이 들어왔다. 순위 자체는 각 쪽 **안에서** 지켜진다.
