정본(`.oculpm/discussion/vibe-code-study-app/discussion.md` 「결론」 §6)이 원칙을 정하고,
`README.md` 가 값을 정하고, **이 문서가 그림을 정한다.** 어긋나면 위가 이긴다.

- 구현: `packages/ui/src/diagram/**` · 계약: `packages/ui/src/diagram/types.ts`
- 진열: `packages/ui/src/dev/Gallery.tsx` (DEV 전용)
- 결정: D182(시각 시스템 전면 교체) · D183(합성 굵게 사고)

## 1. 선 — 그림은 장식이 아니라 본문이다

정본 §6 은 장식을 0 으로 만들었다. **그 절이 지운 것과 이 문서가 만드는 것은 다른 것이다.**
같은 §6 이 「코드와 다이어그램이 가장 큰 요소」라고 적었다.

| | 장식 (§6 이 지운 것) | 그림 (이 문서가 만드는 것) |
|---|---|---|
| 무엇을 나르나 | 아무것도. 분위기를 낸다 | **문항이 묻는 내용 자체** |
| 지우면 | 학습에 손해가 없다 | 문항이 성립하지 않는다 |
| 어디서 나오나 | 취향 | **값**(`bitsOf(0.1, 'f64')`) |
| 예 | 종이 질감 · 도장 · 마스코트 · 판 어긋남 | 비트 배열 · 평가 트리 · 값 상자 |

**넘지 않는 선 넷.** 아래를 어기는 그림은 장식이고, 리뷰에서 되돌린다.

1. 지워도 문항이 성립하면 그것은 장식이다 — 빼라.
2. 데이터에 없는 것을 그리지 않는다. 그림에 나오는 모든 획은 모델의 어떤 칸에서 나온다.
3. 색은 뜻에만. 묶음·범주·종류를 색으로 가르지 않는다 — **줄과 이름**이 가른다.
   그림에서 색이 붙는 자리는 「지금 이것」 한 자리(`--accent`)와 상태 넷뿐이다.
4. 그림이 답을 흘리지 않는다(§4).

## 2. 원칙 넷

**① 데이터에서 결정론으로 만든다.** 손으로 그린 SVG 를 두지 않는다. `bits(0.1, 'f64')` 처럼
값에서 그림이 나와야 문항마다 다시 쓸 수 있다. 실제로 `bitsOf` 는 IEEE 754 를 그대로 읽고,
평가 트리가 접히는 순서는 후위 순회라 같은 트리가 언제나 같은 단계 수를 낸다.

부수 효과가 하나 더 있다 — **그림이 거짓말을 못 한다.** `bitsOf(0.5, 'f64').lossy` 는 거짓이다.
「실수는 다 부정확하다」는 흔한 오개념인데, 손으로 그린 그림은 그 구분을 못 보여 준다.

**② 그림은 답을 흘리지 않는다.** §4.

**③ 정본 §6 을 지킨다.** 색은 뜻에만 · 대비 7:1 · 폭 720~2560 에서 안 깨짐 · 모션 200ms ·
다크 모드. 그림 CSS 에는 애니메이션이 **하나도 없다** — 단계 전환은 상태가 갈리는 것이지
움직이는 것이 아니다.

**④ 읽어 주는 것까지.** §5.

## 3. 그림 목록

### 만든 것 셋

| 그림 | 무엇을 보여 주나 | 언어 | 자리 |
|---|---|---|---|
| **비트 배열** `BitField` | `int` 32비트 · `float` 부호·지수·가수. `0.1` 이 왜 안 떨어지나. 오버플로가 왜 에러가 아니라 값인가. **입력 위젯이 아니다**(§4) | 전부 | `BitField.tsx` |
| **평가 트리** `EvalTree` | `2 + 3 * 4` 가 접히는 순서. 한 단계씩 | 전부 | `EvalTree.tsx` |
| **값 상자** `ValueBox` | 변수 = 이름표가 붙은 상자. 대입은 상자로 내려오는 화살표 | 전부 | `ValueBox.tsx` |
| **걸음 사다리** `EvalTree fold=` | 위와 같은 것을 **낮은 해상도로**. 문항 형식 `step` 의 `fold: FoldStep[]` 를 그대로 받는다 | 전부 | `EvalTree.tsx` |

넷째는 그림이 하나 더 는 것이 아니라 **평가 트리의 입구가 둘인 것**이다. 트리를 실은 문항은
접히는 순서까지 보여 주고, 걸음 배열만 실은 문항은 같은 사다리를 낮은 해상도로 보여 준다.
같은 컴포넌트·같은 예측 규약·같은 표 대체를 쓴다.

셋으로 시작한 이유는 **입문 사용자의 첫 벽 셋**이 여기 있기 때문이다 — 「같은 1 인데 왜
`int` 와 `double` 이 다른가」 · 「왜 `2 + 3 * 4` 가 20 이 아닌가」 · 「`x = x + 1` 이 어떻게 참인가」.

### 명세만, 아직 안 만든 것

만들 자리와 모델 모양이 정해졌고 구현이 없다. **순서는 언어 세션(I4)이 실제 개념 수로 정했다** —
C 2부 아홉 개념 중 여섯이 메모리 줄을 쓰고, C++ 2부 열둘 중 다섯이 스택 프레임을 쓴다.

| 순 | 그림 | 무엇 | 언어 | 모델 스케치 |
|---|---|---|---|---|
| **1** | **메모리 줄** | 주소·연속·포인터. 배열이 왜 0부터인가 | C·C++·Rust·Go·**Java·C#**(java-learning.md·csharp-learning.md 가 「스택의 이름 → 힙의 상자」에 여섯 판을 걸었다) | `{ base: string; stride: number; slots: {addr, value, name?}[] }` — 값 상자의 한 줄 배치판이고, `ValueCell` 에 `addr` 을 더하면 그대로 선다 |
| **2** | **겹친 비트 배열** | **`300u32 as u8` 이 왜 44 인가.** 두 폭을 위아래로 겹쳐 **잘리는 자리**를 보인다 | C·C++·Rust·Go | `{ from: BitsModel; to: BitsModel; keep: number }` — `to.width` 개의 하위 비트만 살아남고 나머지는 잘린 표시. 아래 상자 참조 |
| **3** | **스택 프레임** | 호출이 쌓이고 걷힌다 | 전부 | `{ frames: { fn: string; args: ValueCell[]; locals: ValueCell[] }[] }` — 단계마다 프레임 배열의 스냅숏. `ValueStep` 의 중첩판 |
| 4 | **타입 변환 사다리** | `int` → `double` 은 되고 반대는 잘린다 | 전부 | `{ rungs: { type: NumType; value: string }[]; edges: { from: number; to: number; kind: 'widen' \| 'narrow' \| 'fallible' }[] }` |
| 5 | **소유권 화살표** | 이동·빌림·수명 | Rust | `{ steps: { code: string; owners: {name, holds: string \| null, borrows: string[]}[] }[] }` — 값 상자에 화살표 방향을 더한 것 |

> **겹친 비트 배열이 왜 별도인가.** 지금 `BitField` 는 값 하나를 묶음마다 한 줄로 그린다.
> `300u32 as u8` 은 **두 폭의 관계**라 한 줄짜리로는 안 된다 — 32비트를 그리고 그 아래
> 하위 8비트에 맞춰 8비트를 놓아야 「윗자리가 잘려서 44 가 된다」가 보인다. 두 `BitsModel` 을
> 나란히 놓는 것으로는 부족하다(자리가 안 맞는다). **`BitField` 를 고쳐 쓸 자리가 아니라
> 새 컴포넌트다.**

> **타입 변환 사다리는 비트 배열 둘로 못 대신한다** (I4 확인). 사다리의 화살표가 셋이고
> (러스트의 `as` 뛰어내림 · `From` 올라감 · `TryFrom` 갈라짐) 그것은 **값이 아니라 관계**다.
> 비트 배열은 값 하나를 그리므로 관계를 못 그린다. 그래서 `edges` 가 모델에 따로 있다.

### SQL 전용 넷 — 명세만 (I6 신청)

아홉 언어는 안 쓴다. SQL 챕터가 설 때 만든다. **넷 다 새 종류가 아니라 배치판**이다 —
행 격자와 곱 격자는 표, 진리표는 표, 절 파이프는 걸음 사다리다.

| 그림 | 무엇 | 모델 스케치 |
|---|---|---|
| **행 격자** | 결과 집합이 행 단위로 어떻게 생기나 | `{ cols: string[]; rows: (string \| null)[][]; mark?: {r:number; c:number}[] }` |
| **진리표 3×3** | `NULL` 이 낀 `AND`·`OR` — 참·거짓·모름 | `{ op: 'and' \| 'or'; cells: ('T'\|'F'\|'U')[][] }` — 3×3 고정 |
| **절 파이프** | `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` 가 도는 순서 | `FoldModel` 그대로 — `steps[i].code` 가 절, `type` 이 그 시점의 행 수 |
| **곱 격자** | 조인이 왜 곱인가 | `{ left: string[]; right: string[]; kept: [number,number][] }` |

기존 것 전부 **기존 셋의 확장**으로 잡았다. 새 그림 종류를 늘리는 것보다 배운 규약
(줄·이름·단계·예측)을 다시 쓰는 쪽이 학습자에게도 유지보수에도 싸다.

### 안 만들기로 한 것

| 안 만든 것 | 왜 |
|---|---|
| **애니메이션으로 흐르는 실행 흐름** | 정본 §6 이 모션을 200ms 상한으로 묶었고, 「대기·강조 애니메이션은 없다」로 닫았다. 흐름은 **단계**가 나른다 — 학습자가 자기 속도로 넘긴다 |
| **부동소수점 수직선**(실수 사이의 간격이 벌어지는 그림) | 재미있지만 문항이 묻는 것과 붙지 않는다. 「매력적 곁가지」 g = −0.16 (README §1) 이 정확히 이런 것을 말한다 |
| **색으로 묶음을 가르는 비트 배열** | 부호·지수·가수를 세 색으로 칠하는 것이 흔한 관행인데 §6 이 금지한다. 줄을 나누고 이름을 붙이면 색 없이 더 잘 갈린다 — 색맹 학습자에게도 같다 |

| **SVG 로 그린 손그림 판** | 원칙 ①. 문항마다 다시 못 쓴다 |
| **두 언어 나란히 비교 그림** | 오답이 **다른 언어의 정답**일 때(「그 답은 파이썬의 규칙이다」) 두 언어의 걸음을 나란히 보이는 것은 값이 있다. 그런데 그것은 **배치이지 그림이 아니다** — 사다리 둘을 2단 격자에 넣으면 끝이고, 컴포넌트가 할 일이 없다. 새 종류를 만들면 「나란히」가 셋·넷으로 늘어난다 |
| **「답이 없다」(UB) 전용 그림** | `-O0` 과 `-O2` 가 다른 것을 보이는 자리는 **사다리 둘 + 판정란 한 문장**이면 된다. 그림 쪽이 이미 옳게 되어 있다 — §5 의 「그림은 사실을 그리고, 판정은 `Callout` 이 한다」 때문에 **어느 쪽에도 정답 표시가 안 붙는다.** 「컴파일러마다 다르다」가 아니라 「답이 없고 이 둘이 다른 것이 그 증거다」는 판정란의 문장이 말한다. 그림에 「답 없음」 배지를 다는 쪽이 오히려 그것을 **하나의 답처럼** 보이게 만든다 |

## 4. 예측 → 공개

**학습자가 값을 적기 전에 정답 비트가 보이면 문제가 죽는다.** 그래서 그림 전부
`phase: 'predict' | 'reveal'` 을 받는다.

**「예측」은 그림에 값을 적는다는 뜻이 아니다.** 그림은 **입력 위젯이 아니다** — 답을 적는 칸은
문항 형식이 갖는다(`value` 의 칸 하나, `table` 의 칸 M×N). `predict` 는 그 칸에 답을 적는 동안
그림이 답을 안 흘리는 상태이고, `reveal` 은 답을 낸 뒤 기계의 걸음을 펴는 상태다. 기본값은 `'reveal'` 이다 — 해설·복습 자리가 더 많고,
가리는 쪽은 문항이 명시적으로 켜야 한다.

**무엇을 가리고 무엇을 남기나.** 규칙은 하나다 — **구조는 남고 값이 사라진다.**
학습자는 무엇을 물었는지 알아야 하고, 답은 몰라야 한다.

| 그림 | `predict` 가 가리는 것 | `predict` 에도 남는 것 |
|---|---|---|
| 비트 배열 | 모든 비트 · 묶음 설명(`note`) · 저장된 값 | 묶음 이름 · 각 묶음의 비트 수 · 자리(점선 칸) · 적은 값 |
| 평가 트리 | 접힌 마디의 **값** | 트리 모양 · 접히는 순서 · 지금 몇 단계인지 |
| 값 상자 | **이번 줄에서 바뀐 칸**(`changed`)의 값만 | 코드 줄 · 나머지 칸의 값 · 화살표가 어디로 가는지 |
| 걸음 사다리 | 지금 걸음부터 뒤의 `code` · `type` | **첫 줄(주어진 식)** · 지난 걸음 · 남은 걸음의 자리 |

값 상자가 「바뀐 칸만」인 것이 중요하다. 나머지 칸은 **예측의 재료**다 — `x` 를 가려 버리면
`y = x + 1` 을 예측할 수 없다.

**낭독기로도 안 샌다.** `predict` 에서는 `aria-label` 문장과 표 대체가 함께 가려진다.
그림만 가리고 대체 텍스트가 답을 읽어 주면 가린 것이 아니다.

## 5. 접근성 규약

「화면 낭독기에서 비트 배열이 `1 0 1 1…` 로 읽히면 쓸모없다」가 이 절의 전제다.

**모든 그림이 셋을 가진다.**

1. **`role="img"` + 한 문장 `aria-label`.** 무엇을 뜻하는지를 먼저 말한다. 자동으로 만들어지고
   (`describeBits` · `describeTree` · `describeValues`), 값이 아니라 **뜻**이 문장의 주어다.
   - 예: 「64비트 f64 로 담은 0.1. 묶음은 부호 1비트, 지수 11비트, 가수 52비트.
     실제로 저장된 값은 0.1000…015625 로 적은 값과 다릅니다.」
2. **표 대체.** 한 문장이 못 나르는 칸 단위 정보가 `<table>` 로 들어간다. 화면에서만 숨기고
   (`.dgm-alt` — `clip-path`, `display:none` 아님) 낭독기는 읽는다. 열은 그림마다 다르다:
   비트 배열은 묶음·비트·뜻, 평가 트리는 단계마다 남는 식, 값 상자는 이름·값.
3. **컨트롤이 그림 밖에 있다.** `role="img"` 안의 버튼은 낭독기에서 사라진다. 단계 버튼은
   `figure` 의 형제이고, 그림 자체는 초점을 받지 않는다.

**그 밖에**
- 색만으로 말하지 않는다. 「적은 값과 다르다」는 `--warn` 색과 **글자** 둘 다로 나온다.
- 상태(정답/오답)를 그림에 칠하지 않는다. 그림은 사실을 그리고, 판정은 `Callout` 이 한다.
- 「지금 접히는 마디」는 한 화면에 하나다(신호 주기, README §1).

## 6. 데이터 입력 모양 — 문항이 이것을 준다

전문은 `packages/ui/src/diagram/types.ts`. 아래가 문항 쪽이 알아야 할 전부다.

> **문항 형식과의 접점**(`docs/program/fundamentals.md`). 형식은 넷이고
> (`value`·`step`·`table`·`build`) `bits` 와 `predict` 는 **형식에서 내려갔다** — 「비트 그림이
> 값을 갖는 자리는 틀린 다음이고, 그것은 형식이 아니라 `value` 의 판정란이다」(같은 문서 §2.1).
> 이 문서는 그 판단과 어긋나지 않는다. 그림의 자리는 셋이다:
> ① `value` 의 **판정란**(답을 낸 뒤 기계의 걸음을 편다) ② 비트를 **묻는** `table` 문항의 지문
> ③ 챕터 해설. `predict`/`reveal` 이 곧 「답 내기 전 / 낸 뒤」다.
>
> **값은 문자열로 온다.** `FundValue` 가 `{t:'float', v:'3.0'}` 처럼 값을 문자열로 들기
> 때문이고, 이유는 `3` 과 `3.0` 이 `number` 로는 구별되지 않아서다. `bitsOf` 가 문자열을
> 그대로 받고 적힌 글자를 `literal` 로 보존한다.
>
> **걸음 배열은 그대로 들어간다.** `step` 형식 payload 의 `fold: FoldStep[]` 이
> `EvalTree fold=` 의 입력이다 — 변환이 없다.

### 비트 배열 — 값 하나면 된다

```ts
import { bitsOf, BitField } from '@chickadee/ui';

const model = bitsOf(0.1, 'f64');          // ← 문항이 저장하는 것은 이 두 인자뿐이다
<BitField model={model} phase="predict" caption={t('...')} />
```

`bitsOf(value, type, opts?)`
- `value`: `number | bigint`
- `type`: `'i8'|'i16'|'i32'|'i64'|'u8'|'u16'|'u32'|'u64'|'f32'|'f64'`
- `opts.literal`: 소스에 적힌 글자(`'0.1f'`). 없으면 값을 그대로 찍는다
- `opts.labels`: 묶음 이름 덮어쓰기(`t()` 자리)

내는 것(`BitsModel`)에서 **채점이 쓸 만한 칸**: `bits`(문자열) · `stored`(정확한 십진 전개) ·
`lossy` · `wrapped`. 문항은 `bits` 나 `stored` 를 정답지로 그대로 쓸 수 있다 —
그림과 채점이 같은 함수에서 나오므로 어긋날 수 없다.

### 평가 트리 — 트리와 단계

```ts
const model: EvalTreeModel = {
  expr: '2 + 3 * 4',
  root: { kind: 'op', op: '+', result: '14', kids: [
    { kind: 'leaf', text: '2' },
    { kind: 'op', op: '*', result: '12', kids: [
      { kind: 'leaf', text: '3' }, { kind: 'leaf', text: '4' }] },
  ] },
};
<EvalTree model={model} step={1} onStep={setStep} />
```

- 우선순위는 **트리 모양**이 담는다. 별도 필드가 없다.
- 단계 수 = 연산 마디 수 = `foldSteps(root)`. `step` 은 0(안 접음)부터 그 수까지고,
  범위를 넘으면 잘린다.
- `onStep` 을 안 주면 버튼이 안 생긴다 — 키보드까지 부르는 쪽이 가져가는 자리다.

### 걸음 사다리 — 문항의 `fold` 를 그대로

```ts
// 문항 payload 의 fold: FoldStep[] 를 그대로 넘긴다. 변환 없음.
<EvalTree fold={{ expr: '7 / 2', steps: card.fold }} step={n} onStep={setN} />
```

- `FoldStep = { code: string; type: string }` — 산문이 없다. `7 / 2` → `int / int`, `3` → `int`.
- `steps[0]` 은 **주어진 식**이라 `predict` 에서도 남는다. 걸음 수는 `steps.length - 1`.
- 트리(`model=`)를 실을 수 있으면 그쪽이 낫다 — 사다리는 「무엇이 되었나」를 말하고
  트리는 「**왜 그 순서인가**」까지 말한다. 둘 중 하나만 준다.

### 값 상자 — 단계마다 전체 스냅숏

```ts
const model: ValueBoxModel = {
  steps: [
    { code: 'int x = 3;', cells: [{ name: 'x', type: 'int', value: '3', changed: true, from: '3' }] },
    { code: 'int y = x + 1;', cells: [
        { name: 'x', type: 'int', value: '3' },
        { name: 'y', type: 'int', value: '4', changed: true, from: 'x + 1' }] },
  ],
};
```

- 각 단계는 **차분이 아니라 전체 스냅숏**이다. 앞 단계로 되돌아가도 상태를 다시 계산할 필요가 없다.
- 칸 순서는 단계마다 같아야 한다 — 상자가 자리를 옮기면 학습자가 매번 다시 찾는다.
- `changed: true` 가 **`predict` 에서 가려지는 칸**이자 화살표가 서는 칸이다. 정답지가 그것이다.
- `from` 은 화살표 꼬리에 붙는 글자(`'x + 1'`). 없으면 화살표만 선다.

### 문구는 어디서 오나

그림은 문구를 지어내지 않는다. 캡션·코드 줄·묶음 이름은 **데이터가 나른다.**
그림이 스스로 내는 것은 `packages/ui/src/diagram/labels.ts` 의 열몇 낱말뿐이고
(「이전」·「다음」·「적은 값」·「저장된 값」), **한국어가 정본**이다.
화면은 `labels` 프롭으로 `t()` 문자열을 덮어쓴다.

> **남은 일** — `packages/i18n` 에 `diagram.*` 키가 아직 없다. 키가 생기면
> `DIAGRAM_LABELS_KO` 는 폴백으로만 남는다. 이 세션은 `packages/i18n` 범위를 안 잡아 손대지 않았다.
> 오답 분류 문구(`fund.miss*` 아홉 — other-language·type-drift·ideal-math·rounding·sign·
> spelling·blank·unparsable·unknown)는 **판정란의 것이지 그림의 것이 아니다.** 그림은
> 진단문을 안 싣는다 — §5 의 「그림은 사실을 그리고, 판정은 `Callout` 이 한다」 그대로다.

## 7. 아직 모르는 것

- **52비트 가수가 한 줄에 안 들어간다.** 폭 720 에서 세 줄, 2560 에서 두 줄로 접힌다.
  가로 스크롤·잘림은 0 이지만 「한 묶음이 여러 줄」이 읽기에 얼마나 나쁜지는 안 재 봤다.
  대안(16비트씩 접기, 반복 구간 `0011` 을 묶어 표시)이 있고 실측 없이 고르지 않았다.
- **평가 트리의 깊이 한계를 안 정했다.** 마디가 많으면 `.dgm-view` 가 가로로 스크롤된다
  (화면은 안 밀린다). 입문 문항의 식이 깊어 봐야 잎 일고여덟이라 지금은 문제가 아니지만,
  깊이 5 를 넘는 식에서 어떻게 보이는지는 확인 안 했다.
- **한 문장 `aria-label` 을 실제 낭독기로 듣지 않았다.** 문장이 만들어지는 것은
  단위 시험이 확인했고, VoiceOver·NVDA 에서 어떻게 끊어 읽는지는 못 봤다.
- **`predict` 에서 점선 빈 칸 64개가 어떻게 읽히나.** 「자리가 있다」는 신호는 되는데
  64개가 부담이 되는지, 아니면 아예 묶음별 칸 수만 적는 편이 나은지 안 재 봤다.
- **트리를 실을 것인가 사다리로 둘 것인가.** 입구는 둘 다 열어 뒀다(§6). 사다리는 문항이
  이미 들고 있는 것으로 서고, 트리는 「왜 그 순서인가」까지 말하는 대신 문항 생성기가
  트리를 더 만들어야 한다. **어느 쪽이 입문자에게 값을 더 내는지 안 재 봤다** — 값이 크면
  `step` payload 에 트리를 더하는 것이 결정 사항이다.
- **겹친 비트 배열이 없어 `300u32 as u8` 을 아직 못 그린다.** 모양은 §3 에 적었고 구현이 없다.
  C·C++·러스트 2부가 그것을 요구하므로 메모리 줄 다음 순서다.
