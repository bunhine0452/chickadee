# 03 · 인제스트 · 파싱 · 문법 사전

## 이 문서의 위치

Chickadee 의 **원재료 공장**이다. 사용자 리포(git) → 커밋·파일 선별 → tree-sitter 파싱 → 캡처 → 개념 **사용처(`concept_site`)** 파생, 그리고 그 사용처를 카드로 바꿔 주는 **언어별 문법 사전(YAML)** 의 형식·검증·기여 절차를 정한다. 산출물은 셋이다: Rust 사실 층(01 의 `crates/git`·`crates/parse` + `apps/desktop/src-tauri/jobs.rs`)의 **정책**, TS 파생 층 `packages/concepts`(캡처 → `concept_site`·`import_edge`·`block`·`unit`·`gap`), 사전 저장소 `dictionary/`. 이 문서에서 「chickadee-ingest」는 앞의 두 층을 합쳐 부르는 이름이지 크레이트가 아니다.

| 이 문서가 소유 | 다른 문서가 소유(참조만) |
|---|---|
| 커밋 선별·author 판정·diff 라인 집합·증분·취소 | Rust↔TS IPC 형태, 명령·이벤트 이름 → `01-architecture.md` |
| 언어 감지·문법 크레이트·파서 풀·에러 내성 | sqlite 테이블 DDL, FSRS, 겹(0~4) 계산 → `02-data-model-and-scheduling.md` |
| 개념 id 체계·`.scm` 쿼리·`concept_site` 파생 알고리즘·미지 개념 개수 산출 | 채점(T0 정답 판정·T1 AST 비교·T2 3티어) → `04-grading-engines.md` |
| 사전 YAML 스키마·템플릿 변수·검증·기여 워크플로 | 템플릿 렌더러·`josa`·카드 UI → `05-frontend.md` |
| 문법 구멍 지도 산출 규칙 · 대지(unit) 탐지 | CI 파이프라인·릴리스·사전 배포 채널 → `06-quality-security-release.md` |

## 읽는 순서 / 전제

1. `.oculpm/discussion/vibe-code-study-app/discussion.md` 「결론」 §2(코어 루프·트랙) · §4(최소 미지 개념 우선·개념 전이) · §5(얇은 Rust + 두꺼운 TS, LLM 없이 동작). 이 문서는 그 결정 위에 있으며 바꾸지 않는다.
2. `design/src/ink/data.js` — 카드가 사전에서 무엇을 요구하는지 보여 주는 실물. 이 문서의 YAML 필드는 그 카드 필드와 1:1 로 대응한다(§4 매핑표).
3. `design/ink-home.html` 「판이 없는 문법」 패널 — §6 의 소비자.

한 줄 요약: **HEAD 스냅샷 전체를 파싱해 사용처를 뽑고, 커밋 diff 는 귀속(누가·언제·어느 커밋)과 T2 정답지에만 쓴다. 사전은 개념당 `yaml + scm` 한 쌍이며, 카드 문장은 전부 사용처 값을 치환하는 템플릿이다.**

```
git2 ── 커밋 선별 ── diff hunk ── 커밋→파일·라인 ─────────────┐  (T2 정답지 · 귀속)
      └ HEAD 트리 + 워킹트리 ── 파일 필터 ── 언어 감지 ── 파싱 ─┼─ .scm 실행 ─ capture ─ sqlite ─ TS derive ─ concept_site
                                                              │                                        ▲
dictionary/<lang>/<concept>.{yaml,scm} ───────────────────────┘   TS packages/concepts: 개념 그래프 · 미지 개수 · unit · gap
```

## 1. 인제스트 파이프라인 (git2)

### 1.1 리포 열기

- `Repository::discover(path)`(01 `repo_register` 가 `discover` 를 수행한다) — 사용자가 하위 폴더를 골라도 루트를 찾는다. bare 리포·서브모듈 내부·`.git` 없는 폴더는 거부하고 이유를 돌려준다(「git 리포가 아니에요 — 첫 커밋이 없어도 되지만 `git init` 은 필요합니다」).
- 서브모듈은 v1 에서 건너뛴다(경로 앞머리 매칭으로 제외). 워크트리(`git worktree`)는 지원.
- 커밋 0개 리포도 열린다 — 워킹트리만으로 T0/T1 이 성립하고, T2 는 「정답지가 없다」 상태(discussion 로그: project06 커밋 2개 반례).

### 1.2 author 판정

목적은 두 가지다. ① T2 정답지는 **내(또는 내 AI 세션)가 만든 커밋**이어야 한다 — 남의 커밋을 정답지로 쓰면 「내 코드」 정체성이 깨진다. ② 「AI 가 대신 쓴 자리」 귀속(§6).

- identity 목록 = `settings.identities[]`(`{email, name}`, D46). 첫 열기 때 자동 제안: `git config user.email/user.name`(로컬 → 글로벌) + 리포 커밋 author 상위 5명. 선택 UI 는 05.
- 매칭 순서: (1) `.mailmap` 적용(`repo.mailmap()` → `commit.author_with_mailmap`) (2) email 소문자 완전 일치 (3) GitHub noreply `NNN+login@users.noreply.github.com` 은 `login` 을 등록 이름과 대소문자 무시 비교 (4) 이름 정규화(공백·점 제거, 소문자) 완전 일치. 부분 일치는 하지 않는다 — 「Kim」 이 「Kim Hyunbin」 을 잡으면 오탐이 더 많다.
- Rust 는 mailmap 을 적용한 `author_email`·`author_name` 을 `git_commit` 에 저장하고, 매칭 (2)~(4) 는 TS `packages/concepts/commits.ts` 가 `settings.identities` 로 판정해 `git_commit.author_matched` 파생 열에 쓴다. **사용처 추출은 author 를 보지 않는다** — 리포에 있으면 내 앱의 일부이고 읽어야 한다.

### 1.3 읽는 커밋

`revwalk` 를 HEAD 에서 `TOPOLOGICAL | TIME` 으로 걷는다. **first-parent 단순화는 쓰지 않는다**(왜: 머지 브랜치 안의 기능 커밋이 통째로 숨는다 — 브랜치 워크플로 리포에서 T2 정답지가 전부 사라진 경험).

판정은 TS `commits.ts` 가 `parent_count·author_*·subject·files_n·insertions` 로 하고 `git_commit.kind` 에 쓴다. Rust 는 분류를 모른다.

| 분류 `kind` | 판정 | 처리 |
|---|---|---|
| `merge` | `parent_count() > 1` | diff 계산 안 함. 조상은 계속 걷는다 |
| `revert` | 제목이 `Revert "` 로 시작 | 라인 귀속엔 포함, T2 정답지에서 제외 |
| `bot` | author email/name 이 `dependabot|renovate|\[bot\]|github-actions|noreply@github.com(머지 봇)` 또는 제목이 `chore(release)|Bump version|Merge (branch|pull request)` | 전부 제외 |
| `bulk` | 변경 파일 ≥ 200 **또는** 추가 줄 ≥ 5,000 (스캐폴딩·초기 커밋) | 라인 귀속엔 포함, T2 정답지에서 제외 |
| `normal` | 나머지 | 전부 사용 |

파일 필터 — 트리 순회와 diff 모두에 같은 함수 `is_ingestible(path, blob)` 를 쓴다. 아래 목록은 `packages/concepts/ingest-defaults.ts` 의 `EXCLUDE_GLOBS`·`GENERATED_MARKERS` 상수이며 `IngestSpec` 으로 Rust 에 전달된다. `linguist-generated` 는 Rust 가 `repo.get_attr` 로 본다.

- 경로 앞머리 제외: `node_modules/ dist/ build/ out/ .next/ target/ vendor/ Pods/ .dart_tool/ DerivedData/ __pycache__/ .venv/ venv/ coverage/ .turbo/ .expo/ android/app/build/`.
- 파일명 제외: lock(`package-lock.json pnpm-lock.yaml yarn.lock bun.lockb Cargo.lock pubspec.lock Package.resolved poetry.lock uv.lock go.sum`), `*.min.js *.map *.d.ts *.g.dart *.freezed.dart *.pb.go *_pb2.py *.generated.*`.
- 생성 파일 마커: 첫 5줄에 `@generated` / `DO NOT EDIT` / `<auto-generated` / `Code generated by`. `.gitattributes` 의 `linguist-generated=true` 도 존중(GitHub 관례 재사용).
- 크기: blob > 512 KB 스킵. 바이너리: `Blob::is_binary()`(첫 8000 바이트 NUL).
- 리포별 추가 제외 목록은 `settings.exclude_globs`. 별도 dotfile 은 만들지 않는다(YAGNI).

### 1.4 diff hunk → 라인 집합

커밋마다 `diff_tree_to_tree(parent_tree, tree, opts)` 를 **첫 부모** 기준으로 낸다(머지는 계산 안 하므로 부모는 항상 하나).

- `DiffOptions`: `context_lines(0)`, `ignore_whitespace(true)` — 포맷팅만 바뀐 파일은 0/0 이 되어 T2 후보에서 자연히 빠진다, `include_typechange(false)`.
- `diff.find_similar(renames(true), rename_threshold(50))` — 왜: 리네임을 삭제+추가로 세면 파일 하나가 500줄 「추가」로 잡혀 `bulk` 오판과 T2 정답지 오염을 일으킨다.
- 델타별로 `Patch::from_diff` → hunk → `origin == '+'` 인 줄의 `new_lineno` 를 범위로 압축. 수정은 `-`/`+` 쌍이지만 **새 쪽 줄만** 저장한다(옛 줄은 HEAD 에 없다).

저장 형태는 02 `git_commit`(`kind`·`author_matched` 는 TS 파생 열) + `commit_file`(`path old_path status additions deletions touched_json`). TS 타입은 02 §8.2 `CommitFile`. 커밋 본문은 저장하지 않는다(제목만).

`commit_file` 이 곧 **T2 정답지의 재료**다(data.js `T2.commit`·`core`·`sec` 의 `+64 −0` 통계, `isNew` = `status==='A'`). core 임계는 D5 `core = { status==='A' ∨ additions+deletions ≥ 5 ∨ 유닛 진입점 }`, sec/trap 구분과 해설 문장은 04 §8.1 이 정한다.

### 1.5 사용처 귀속(2차 패스)

Site 에 `commit` 을 붙이려면 blame 이 필요한데 `git blame` 은 파일×커밋 수에 비례해 대형 리포에서 분 단위다(왜: 1차 패스에 넣었다가 첫 화면이 3분 걸린 실패). 그래서:

- 1차 패스는 blame 없이 끝나고 카드가 만들어진다(`site.commit = null`).
- 2차 패스는 TS `packages/concepts/blame.ts` 가 Site 가 있는 파일마다 01 `git_blame_lines{repoId, relPath, rev}` 를 배경에서 호출해 `BlameHunk[]` 로 `concept_site.commit_id` 를 채운다. Rust 쪽은 `blame_file(BlameOptions::newest_commit(HEAD).track_copies_same_file(false))`, 2초 초과 시 `GIT_BLAME_TIMEOUT` 이고 그 파일은 포기(경고 이벤트 아님, TS 로그).

### 1.6 증분

상태는 02 `ingest_run` + `repo.head_sha` + `file.content_hash`(git blob oid) 뿐이다.

1. 새 HEAD 를 읽고 `find_commit(old_head)` 가 실패하면(gc 됨) **전체 재인제스트**.
2. `merge_base(old_head, new_head)` = `old_head` 면 정상 전진: `revwalk.push(new_head); hide(old_head)`.
3. 다르면 rebase/force-push: `old_head` 쪽에만 있던 커밋은 `git_commit.is_reachable = 0`(삭제 금지 — 학습 기록이 참조한다). `merge_base..new_head` 를 걷는다.
4. 파일 단위 증분: `diff_tree_to_tree(old_tree, new_tree)` 한 번으로 바뀐 파일 목록을 얻고 **그 파일만 재파싱**. `file.content_hash` 가 같으면 건너뛴다(01 §3.3).
5. Site 의 정체성은 줄 번호가 아니라 `concept_site.site_key = fnv1a64(concept, path, shape, occurrence)` (§3.5, TS 파생 · D70) 라 줄이 밀려도 학습 기록이 살아남는다. 재파생 후 같은 key 는 갱신, 사라진 key 는 `is_alive = 0`.

### 1.7 워킹트리 미커밋 변경

`repo.statuses(StatusOptions::include_untracked(true).recurse_untracked_dirs(true))` — git2 가 `.gitignore` 를 적용해 준다. 변경·미추적 파일은 디스크에서 읽어 파싱한다. Rust 가 `file.head_oid` 와 `content_hash` 를 비교해 `file.is_dirty` 를 쓰고 TS 가 `concept_site.is_dirty` 로 복사한다. 카드의 `rev` 는 dirty 파일이면 `null`(워크트리). 왜: 바이브 코더의 리포엔 커밋 안 된 작업이 늘 있고 그것도 「내 코드」다. 단 T2 정답지엔 들어가지 않는다. 재스캔 시점은 리포 열기·세션 시작 직전·수동 새로고침 세 곳 — 셋 다 TS 가 `ingest_start{mode:'incremental'}` 를 부른다. 파일 워처는 두지 않는다(왜: `node_modules` 이벤트 폭주).

### 1.8 진행률 이벤트와 취소

이벤트는 01 §3.2 의 `ingest_progress`(phase `walk|parse|git|write`) · `ingest_warning{jobId, relPath, reason}` · `ingest_done` · `ingest_error`. `reason` = `oversize | parse-poor | timeout | binary | generated | long-line`.

취소는 `Arc<AtomicBool>`. 커밋 1개·파일 1개 단위로 검사하고, sqlite 는 **500행 tx**(01 §3.3)라 취소해도 커밋된 배치는 남는다. `ingest_run.status = 'cancelled'` 로 남기고, 다음 실행은 `incremental` 이 해시로 이어간다.

## 2. 파서 계층

### 2.1 언어 감지

| `.tsx` | `tsx` | |
| `.js .mjs .cjs .jsx` | `javascript` | JSX 포함 |
| `.py` | `python` | `.pyi` 제외 |
| `.go` | `go` | |

### 2.2 문법 크레이트와 품질 리스크

tree-sitter 러스트 바인딩은 `tree-sitter` 0.23+ 의 `LANGUAGE` 상수 방식(`tree_sitter_typescript::LANGUAGE_TYPESCRIPT` 등)을 쓴다. **모든 문법 크레이트는 같은 ABI 버전에 맞춰 Cargo.lock 에 고정하고 한꺼번에 올린다.** 왜: 문법 한 개만 올렸다가 노드 이름이 바뀌어 `.scm` 이 조용히 0건을 내는 것이 가장 흔한 회귀다. 올릴 때는 §8 골든 전체가 문이다. (정확한 버전 번호는 구현 시점에 crates.io 로 확인.)

| 언어 | 크레이트 | 유지 주체 | 리스크 | 대응 |
|---|---|---|---|---|
| TS/TSX | `tree-sitter-typescript` | tree-sitter org | 낮음 | 기준 언어 |
| JS/JSX | `tree-sitter-javascript` | org | 낮음 | TS 와 매개변수 구조가 달라 쿼리 분기 필요(§3.2) |
| Python | `tree-sitter-python` | org | 낮음 | |
| Go | `tree-sitter-go` | org | 낮음 | |
| Rust | `tree-sitter-rust` | org | 낮음 | 매크로 내부는 `token_tree` 라 미해석 |
| Swift | `tree-sitter-swift`(alex-pinkus) | 커뮤니티 | **중간** — parser.c 가 수십 MB 라 빌드 느림, 결과 빌더·매크로·Swift 5.9+ 일부 ERROR | ERROR 비율 게이트(§2.3), 골든 20파일 통과 전 사전 미공개 |
| Dart | `tree-sitter-dart`(UserNobody14) | 커뮤니티 | **높음** — 릴리스 불규칙, crates.io 미배포 구간, Dart 3 records/patterns 미지원 가능 | git 의존 + 커밋 고정 + 벤더링; 품질 미달 시 언어 보류(열린 질문) |
| SQL | `tree-sitter-sequel`(DerekStride) | 커뮤니티 | 중간 — 방언 혼합, `$$` 함수 본문 ERROR | 파일 단위 `parse-poor` 허용, SELECT/JOIN 등 단순 개념만 |

### 2.3 파싱 에러 내성

tree-sitter 는 항상 트리를 돌려준다. 정책은 파일과 사용처 두 층이다.

- 파일: `ERROR`+`MISSING` 노드의 바이트 합 / 파일 바이트 > 5 % **또는** 단일 ERROR 가 40줄 초과 → `parse_quality = 'poor'`. 쿼리는 그래도 돌리되 `Warning{parse-poor}`. 값은 `file.parse_quality` 에 쓴다.
- 사용처: Rust 는 캡처마다 `inError`(ERROR 겹침 또는 조상 3단 안 ERROR)만 표시하고, 버리는 것은 TS `derive.ts` 가 한다. 왜: 복구 영역 안의 노드는 지목 토큰 위치가 틀리고, 커뮤니티 문법일수록 복구가 엉뚱하다.
- 파일 단위 타임아웃 2초(0.25 는 `ParseOptions` 진행 콜백에서 취소 플래그 확인, 그 이전은 `set_timeout_micros`).

### 2.4 파서 풀·스레딩

- `Parser` 는 `Sync` 가 아니다. parse 풀 `min(4, cores − 1)`(01)에서 `thread_local! { HashMap<Grammar, Parser> }` 로 스레드당 문법별 파서를 지연 생성한다.
- `Query` 는 `Send + Sync` 라 **(문법, 개념)당 한 번 컴파일해 `Arc` 로 공유**. `QueryCursor` 는 스레드당. `set_match_limit(1024)`.
- 파일 하나 = 작업 하나. 트리는 쿼리 직후 버린다(메모리 예산 §7). 캡처는 500행 tx 로 쓴다(01 §3.3).
- T1 AST 비교(04)도 같은 풀·같은 파서를 쓴다 — 별도 파서를 만들지 않도록 01 `parse_snippet` 명령(`AstLite`)을 쓴다.

### 2.5 큰 파일 정책

| 조건 | 처리 |
|---|---|
| > 512 KB | 스킵 + `Warning{oversize}` |
| > 5,000 줄 | 파싱은 하되 TS 가 `file.line_count` 로 `concept_site.is_oversize` 를 세운다; 개념당 Site 상한 20개(앞에서부터), 카드 대상에서 후순위 |
| `@site` 가 12줄 초과 | Site 는 남기되 `is_oversize = 1`, 카드 대상 제외(TS), 「다른 사용처」 목록에만 |

### 3.2 tree-sitter 쿼리(.scm)

캡처 이름 규약(린트가 강제한다):

| 캡처 | 개수 | 뜻 |
|---|---|---|
| `@site` | 패턴당 정확히 1 | 사용처 범위. `line` = 시작 행 |
| `@pick.N` (1~9) | 0~9 | 지목형에서 짚을 수 있는 토큰. 반드시 `@site` 안. 사전의 `point.answer` 가 N 을 가리킨다 |
| `@hole` | 0~1 | 빈칸형에서 지울 토큰. 텍스트가 사전 `blank.options` 의 정답과 같아야 한다 |
| `@ctx.<name>` | 자유 | 템플릿 변수(`{{ctx.fallback}}`). 없으면 mustache 섹션으로 분기 |
| **맥락 패턴** | — | 캡처가 `@ctx.*` 뿐이고 `@site` 가 없는 패턴. 매치의 최외곽 노드 범위 **안에 있는 같은 개념의 Site 전부**에 ctx 를 붙인다. 사용처를 만들지 않는다 |
| `(#set! form "…")` | 패턴당 0~1 | 같은 개념의 형태 이름(`member`·`call`). 골든·통계에 쓴다 |

**시스템 쿼리(언어당 2파일)**: `_imports.scm` — 패턴마다 `@import.source`(지정자 문자열 노드) 1개와 `(#set! form "static"|"type"|"dynamic"|"require")`; `_blocks.scm` — `@block.function`(04 §3.1 표의 노드) 1개 + `@block.name` 0~1개. 캡처 이름 정규식 `^(site|pick\.[1-9]|hole|ctx\.[a-z_]+|import\.source|block\.(function|name))$`. 경로 해석·블록 분절은 TS(04).

린트 규칙은 「패턴은 `@site` 정확히 1개를 갖거나, `@ctx.*` 만 갖는 맥락 패턴이다」. 매치 정렬은 `(span.start, span.end)` 오름차순(TS `derive.ts` 가 `match_id`·`start_byte` 로 정렬) — 같은 자리에서 시작하면 안쪽(짧은 것)이 먼저다.

TS 와 JS 문법은 화살표 함수 매개변수 구조가 다르다(TS: `formal_parameters > required_parameter(pattern)`, JS: `formal_parameters > identifier`). 구조가 다른 패턴은 tree-sitter 가 「impossible pattern」으로 컴파일을 거부하므로 **문법별 파일로 나눈다** (`queries: [{grammars:[typescript,tsx], file}, {grammars:[javascript], file}]`). 아래는 TS 판.

### 3.4 실행 절차 (파일 하나)

두 층으로 나뉜다.

**Rust**(01 §3.3):

1. 언어 감지된 파일을 파싱 → 트리.
2. 등록된 모든 쿼리를 실행하고, 캡처를 `match_id`·`pattern_index`·`form`·`in_error`·행/열과 함께 저장한다.
3. `parse_quality` 저장 → 트리 폐기.

**TS `derive.ts`**(파일 단위):

1. 캡처를 `match_id` 로 묶고, `inError` 인 `site` 매치는 폐기한다(§2.3).
2. 맥락 패턴 ctx 를 병합한다 — 같은 개념 Site 중 범위 안에 드는 것에 붙이되 Site 자체 ctx 가 우선.
3. **행 인덱스**로 각 Site 의 `lineConcepts` 와 `uncoveredRatio` 를 계산한다. 바닥 개념(`ts/call-expression` 등)이 여기서 덮개 역할을 한다.
4. `shape` 계산(04 §0 토크나이저로 `id`→`_`, 리터럴→`#`).
5. `(concept, path, shape)` 별 `occurrence` → `site_key` → `concept_site` upsert.

### 3.5 같은 개념 중복 제거

- 파일 안: `(concept, shape)` 가 같으면 **첫 것만 카드 대상**, 나머지는 `occurrence ≥ 1` 로 저장만(「다른 사용처」에 쓴다).
- 파일 간: 전부 저장. 카드 선택은 TS 가 `shape` 다양성으로 한다 — `products.map(p => <X/>)` 스무 줄이 20장이 되지 않도록.
- 겹(0~4)은 개념 단위이므로 Site 가 몇 개든 덱은 개념 수만큼이다(discussion §2 덱 폭발 방지).

### 3.6 「미지 개념 개수」 산출 (TS, 값은 `derive.ts` 가 준비)

이 절이 공식의 **정본**이다 — 02 `unknown_count` 는 이 함수의 캐시다.

```ts
function unknownCount(site: ConceptSite, layerOf: (c: string) => 0 | 1 | 2 | 3 | 4, dict: Dictionary): number {
  const prereqs = dict.prereqClosure(site.conceptId, /*depth*/ 2);        // 사전 prereq[] 를 2단까지
  const candidates = new Set([...site.lineConcepts, ...prereqs]);
  candidates.delete(site.conceptId);
  let n = [...candidates].filter((c) => layerOf(c) === 0).length;
  if (site.uncoveredRatio > 0.5) n += 1;                                  // 사전이 모르는 것도 「미지」
  if (site.lineEnd - site.lineStart >= 3) n += 1;                         // 긴 사용처 불리
  return n;
}
```

`unknownCount` 가 재는 것은 **초점 줄**이다. 판이 보여 주는 것은 줄이 아니라 **창**(D141 — 감싸는 블록 ∪ 초점 ±2, 상한 40줄)이므로 창을 따로 센다 (D155):

```ts
function windowUnknown(site, block, index, layerOf): number {
  const win = windowRange(site.lineStart, block);              // 판이 그리는 창과 같은 함수
  const ids = new Set<string>();
  for (let n = win.from; n <= win.to; n += 1)
    for (const id of index.get(n) ?? []) if (id !== site.conceptId) ids.add(id);
  return [...ids].filter((id) => layerOf(id) === 0).length;
}
```

첫 노출 = `unknownCount` 최소 → 동률이면 **`windowUnknown` 최소** → `uncoveredRatio` 오름차순 → 짧은 사용처 → `dirty=false` 우선 → 경로. `unknownCount > 3` 인 사용처는 겹이 오를 때까지 보류 — 이것이 §4 「난이도 곡선이 파생된다」의 구현이다. 문턱은 초점 줄 기준 그대로이고 창은 **순서만** 정한다. `const MAX = 10` 은 lineConcepts = {const-declaration, number-literal} 로 0~1, `const [c, setC] = useState(0)` 은 {const, array-destructuring, call, react/use-state} 로 3~4 가 된다.

**왜 창을 따로 세나** (D155): 초점 줄만 보면 1,747줄짜리 파일 한복판의 두 글자짜리 리터럴이 만점을 받는다. 실측 리포에서 `ts/number-literal` 사용처 261곳 중 미지 0 인 다섯이 동률이 되었고, 마지막 동률 처리가 경로 알파벳순이라 **가장 큰 파일이 이겼다** — 「숫자」의 첫 판이 `function Spark({ data, w = 56, h = 16 }: { data: number[]; w?: number; h?: number })` 로 나갔다. `const MIN_FONT = 9;` 가 같은 후보 안에 있었다. 창을 넣으면 창 14줄·미지 10 에서 5줄·미지 0 으로 옮겨간다.

`uncoveredRatio`(> 0.5 면 +1)가 이것을 잡았어야 했는데 같은 리포 4,488 사용처의 평균이 0.00 이라 **한 번도 걸리지 않는다** — 감싸는 사용처의 바이트 범위가 안쪽 토큰을 전부 「덮은 것」으로 치기 때문이다. 그 자리는 따로 본다.

| `result` `{label, value, note}` | `result` | 값 추적 결과 |

### 4.3 템플릿 변수 치환 규약

문장 값은 전부 **mustache 부분집합** 템플릿이다: `{{var}}` · 섹션 `{{#ctx.fallback}}…{{/ctx.fallback}}` · 부정 `{{^…}}…{{/…}}` · 필터 `{{pick.1|josa:이,가}}`. HTML 은 `<code> <b> <i> <em> <br> <kbd>` 6종(06 §4.2 와 같은 목록), 속성 0 — 그 외는 이스케이프.

| 변수 | 값 |
|---|---|
| `{{site.line}}` `{{site.text}}` `{{site.form}}` | Site 필드 |
| `{{file}}` `{{file.base}}` | 경로 / 파일명 |
| `{{pick.N}}` `{{pick.N.line}}` | N번 토큰 텍스트 / 그 행 |
| `{{hole}}` | 빈칸 원문 |
| `{{ctx.<name>}}` | `@ctx.*` 캡처 |
| `{{other.file}}` `{{other.line}}` `{{other.text}}` | 같은 개념의 다른 Site(사다리 3단·혼동 쌍 비교) |
| `{{x|josa:이,가}}` | 받침 유무로 조사 선택(`design/src/ink/util.js` 의 `josa` 와 같은 규칙, 05 가 구현) |
| `{{x|code}}` | `<code>` 로 감싸고 이스케이프 |

**규칙: 변수 바로 뒤에 조사를 직접 쓰지 않는다** (`{{pick.1}}가` 금지 → `{{pick.1|josa:이,가}}`). 변수가 `res.user` 인지 `'손님'` 인지 모르므로 하드코딩 조사는 반드시 틀린다.

**로케일 (D117 · D118).** 사람이 읽는 문자열은 `{ ko, en }` 두 벌이다 — `name` 은 이미 그 모양이고 `dict.one_liner` · `dict.why` · `dict.trace[]` · `rule` · `ok` · `payoff` · `bridge` · `misconceptions[]` · `result.label` · `result.note` · 문항의 `q` · `hint` · `options[].t` · `diag.t` · `diag.edge.h` · `why_gate.q` · `why_gate.help` · `why_gate.choices[].t` · `.fb` 가 같은 규칙을 따른다. 위 예시는 `ko` 만 적은 축약형이고 **문자열 자리에 스칼라를 쓰면 `ko` 로 읽는다** — 기존 57 파일이 손대지 않고 통과하며 `en` 은 채우는 대로 붙는다. `en` 이 없으면 로더가 `ko` 로 폴백하고 판에 그 사실을 한 줄로 적는다(빈 칸을 그리지 않는다). 조사 필터 `{{…|josa:…}}` 는 `en` 에서 항등이므로 en 문자열에 쓰지 않는다(§5.1 린트). 개념 이름의 `en` 은 **용어집 `dictionary/_glossary.en.yaml` 이 정본**이다 — 같은 개념이 파일마다 다른 영단어로 나가는 것을 막는 유일한 자리이고, 사용자가 검수하는 지점도 여기 하나다.

의미형은 옵션 4개(정답 1 + 진단 3), 지목형은 `diag` 가 오답 pick 마다 있어야 하고, 빈칸형은 옵션 4개 중 오답 3개가 `confusions` 에 있는 개념의 토큰이어야 한다. `why_gate.choices` 는 3개·`ok` 1개(린트).

`no_hole_reason` 은 **부채를 갚는 글이 아니라 부채가 아님을 밝히는 글**이다(D145). 「아직 안 썼다」와 「이 문법에는 뚫을 구멍이 없다」는 다른 상태인데 게이트는 그 둘을 구별할 수 없다 — 사람이 적어야 구별된다. 빈칸형이 생긴 뒤에도 남아 있으면 린트가 잡는다(`no-hole-reason-stale`): 표는 초록인데 이유는 거짓말인 상태를 만들지 않는다.

**사전 저작 부채 게이트 (D145).** 위의 린트는 **틀린 것**을 잡는다 — 통과가 곧 정답이라 임계가 없다. 그와 별개로 `pnpm dict:lint` 는 **아직 안 쓴 것**을 세어 표로 찍는다(`authoringDebt`). 규칙 넷:

| 규칙 | 대상 | 무엇을 센다 |
|---|---|---|
| `blank-or-reason` | `_lang.yaml` 의 `essential` | `blank:` 절과 `@hole` 캡처를 **둘 다** 갖거나, `no_hole_reason` 에 못 갖는 사유를 적었나 |
| `point-picks` | `point:` 가 있는 개념 전부 | 그 개념 `.scm` 이 `@pick.N` 을 **3개 이상** 내나 (정답 1 + 오답 3 이 나오는 최소값, `packages/cards/src/t0-point.ts`) |
| `why-gate` | `essential` | `why_gate:` 가 있나 |
| `zero-one-liner` | 0장 후보 = `essential` ∧ 그 집합 안에서의 선행 깊이 ≤ 1 (D136) | `one_liner` 가 그 개념 문항의 **정답 토큰을 글자로 내지 않나** (D138) |

임계는 D132 와 같은 **래칫**이다 — 오늘의 실측을 바닥으로 두고 **목표(대상 전량)를 나란히 적고 표를 매번 찍는다**. 임계를 오늘 값에 맞춰 두고 목표를 지우면 그 거리가 안 보인다. 사전을 채우면 `dict.test.ts` 의 `DEBT_RATCHET` 을 **올린다**. 2026-09-04 실측: `blank-or-reason` 2/23 · `point-picks` 18/26 · `why-gate` 0/23 · `zero-one-liner` 3/6.

`zero-one-liner` 의 대상이 실제 0장 대지의 8장이 아니라 **후보 전량**인 이유: 어느 8장이 뽑히는지는 리포마다 다르고 사전만 보고는 알 수 없다. 어느 것이 뽑혀도 새면 안 된다. 검사는 태그와 문장 끝 마침표·쉼표를 걷어낸 뒤에 본다 — `.` 이 정답인 개념(`ts/property-access`)에서 한국어 문장의 마침표까지 걸리면 통과할 수 없는 규칙이 되기 때문이고, 식별자 꼴 토큰은 낱말 경계로 본다(`prev` 가 `previous` 안에서 걸리면 안 된다).

**왜 부채가 게이트여야 하나.** 개념 하나가 YAML 150~230줄이고 `ko`/`en` 양쪽이라 사전은 이 리포에서 가장 비싼 손 작업이다. 게이트가 없으면 미뤄지는 것이 기본값이고, `blank:` 2편·`why_gate:` 0편이 그 증거다. 그 결과가 판 유형 쏠림으로 나온다 — `tests/support/quality.test.ts` 의 `KIND_SHARE_RATCHET`(의미형 99.5%)과 이 표는 같은 원인의 앞뒤이고, 그 게이트의 드롭 사유 「짚을 후보가 3개에 못 미친다」·「이 사용처에는 구멍(@hole)이 없다」가 여기 두 줄에 그대로 대응한다. **저 상수를 내리는 일은 이 표를 채우는 일이다.**

### 5.2 커뮤니티 기여 워크플로

PR 템플릿 항목: (1) 개념 id 와 `universal` 판단 근거 (2) 이 문법이 실제 리포에서 어떻게 보이는지 링크 1개 이상 (3) `examples` 양성 2·음성 1 이상 (4) 오답 진단이 「그것이 참이 되는 조건」 형식인지 자가 체크 (5) `pnpm dict:lint` 와 `cargo test` 통과 로그 (6) 한국어 본문 검토자 태그(`@dict-ko`) (7) **LLM 초안을 썼는지와 어디에 썼는지**. 새 언어는 `_lang.yaml` + 바닥 개념 10개 + 골든 20파일이 최소 단위.

**목록은 밖에서 참고하고 간선은 우리가 매긴다 (D148).** 새 언어·새 바닥 개념의 **목록**은 [Exercism](https://github.com/exercism) 트랙의 `config.json`(MIT · © 2021 Exercism)을 참고 출처로 쓴다 — 무엇이 그 언어의 바닥인가에 대한 남의 답이 이미 있고, 우리 판정과 갈리면 갈린 이유를 PR 에 적는다. 다만 그 파일의 `prerequisites` 는 **가져오지 않는다**: 그쪽 값은 *연습문제를 여는 조건*이고 우리 `prereq` 는 *개념 이해의 선행*(§3.1)이라 뜻이 다르다. JS 트랙의 `functions` 가 깊이 6(선행 `objects · arrays · null-undefined`)인 것이 그 차이다 — 함수가 배열보다 어려워서가 아니라 그 연습이 객체·배열을 다루기 때문이고, 간선을 그대로 쓰면 함수 정의가 0장(깊이 ≤ 2, D147)에 영영 못 들어온다. **산문은 베끼지 않는다** — 문장을 가져오는 순간 MIT 고지 의무가 생기고, 사전 산문은 아래의 LLM 초안 + 사람 검토 경로로 쓴다.

**LLM 초안은 권장한다 (D144).** 이 자리는 「허용」이었고 「권장」으로 올린다 — 부채 표(§5.1)가 비어 있는 칸을 개념 단위로 세고 있고, 그 칸을 메우는 일(`.scm` 의 `@hole`·`@pick.N` 자리 · `blank:` 절 · `why_gate:` 문항 · 새 언어의 개념 초안)은 초안이 있으면 몇 배로 빠르다. 대신 **PR 본문에 어디에 썼는지 적고, 사람이 예시를 실제로 돌려 본다.**

**LLM 은 저작 시점에만 쓴다 — 실행 시점에는 쓰지 않는다 (D144).** 산출물이 리포에 커밋되는 YAML 이므로 **키가 없는 사용자에게 똑같이 도착한다**. 실행 시 생성·채점 경로는 열지 않는다. 안티패턴 네 행이 그대로 남고, 사다리 4단은 D106 대로 프롬프트 생성·복사에 머문다:

| 어디 | 기각한 것 |
|---|---|
| 04 §1.4 | LLM 으로 보기·진단 생성 |
| 04 §4.6 | LLM 「같은 뜻인가」 판단(T1 채점) |
| 이 문서 「대안과 버린 이유」 | 사전 문장을 LLM 이 실행 시 생성 |
| 06 「대안과 버린 이유」 | 채점 테스트에 LLM 판정 대조 |

이 경계가 도구가 아니라 **검증 위치**의 문제인 이유는 §5.1 의 검증기 목록에 있다 — 기계가 보는 것은 스키마·참조·캡처 자리·`examples` 파생·템플릿 변수·문체이고, 그 목록에 **없는** 것이 둘 있다: 의미형이 주장하는 **값이 참인가**, 그리고 「그것이 참이 되는 조건」 **진단문이 참인가**. 실행 없이 판정할 수 없어 사람의 PR 리뷰가 유일한 방어이고, 저작 시점에는 그 방어가 있고 실행 시점에는 없다.

### 5.3 버전과 앱 호환

- 사전 파일의 `schema: N`. 앱은 `SUPPORTED_DICT_SCHEMA = [1]`. 선택 필드 추가는 같은 N, 의미 변경·필수 추가는 N+1.

## 6. 문법 구멍 지도

- `ts/_lang.yaml`:

```yaml
lang: ts
grammars: [typescript, tsx, javascript]
grammar_abi: 14
essential:            # 「필수 문법」 순서 = 위상 정렬 동률 시 순서. 30~50개
  - ts/const-declaration
  - ts/arrow-function
  - ts/property-access
  - ts/undefined-null
  - ts/array-destructuring
  - ts/optional-chaining
  - ts/nullish-coalescing
  - ts/async-await
  - ts/try-catch
  - ts/generics
  # …
alternatives:          # 「AI 가 대신 쓴 것」 — 구멍 개념 ↔ 같은 일을 하는 다른 표기
  - { gap: ts/async-await, present: ts/promise-then, note: "같은 일을 두 표기로 — AI 가 섞어 썼습니다" }
  - { gap: ts/nullish-coalescing, present: ts/logical-or-default }
  - { gap: ts/optional-chaining, present: ts/logical-and-guard }
  - { gap: ts/array-destructuring, present: ts/index-access-pair }
thin_threshold: { min_files: 2, min_sites: 3, small_repo_files: 20 }
diag_default:          # point[].diag 가 없는 pick · blank 폴백 진단 (04 §2.1)
  point: "«{{pick}}» 은 {{role}} 자리입니다. {{concept}} 는 «{{answer}}» 입니다. {{rule}}"
  blank: "«{{pick}}» 은 이 자리에 오지 않습니다. {{rule}}"
```

- 집계(TS, 리포 열 때와 인제스트 후): `essential` 개념마다 `count = |sites|`, `files = |distinct path|`, `layer` = 사용자 겹.
- **표본 부족** `thin`: 언어 파일 ≥ `small_repo_files` 인 리포에서 `files < min_files || count < min_sites`. 작은 리포는 `count ≥ 1` 이면 충분. `thin` 이면 사다리 3단(다른 사용처)을 끄고, 사전 `examples` 의 합성 예시를 쓰되 반드시 「곧 {{file.base}}:{{site.line}} 에서 봅니다」 예고를 붙인다(discussion §4).
- **판이 없는 문법** 패널 = `count > 0 && layer == 0` 인 essential 개념, `count` 내림차순, 상위 1개 또는 `count ≥ 10` 은 `hot`, 막대 `--f = count / max(count)`. `count == 0` 인 필수 문법은 패널에 **안 나온다**(패널 정의가 「내 코드엔 있는데」다). 그런 개념은 사용자가 그 언어가 처음일 때만 「0장 — 이 언어의 바닥」에 합성 예시로 나온다 — 0장의 정의와 담기는 규칙은 **02 §6.2** 가 소유하고, 대지를 쓰는 것은 `writeZeroChapter` 다 (D136). **리포에 사용처가 아예 없는 개념은 0장에도 담지 않는다**: 「곧 네 코드 어디에서 본다」를 예고할 자리가 없으면 합성 예제를 만들지 않는다(D137, 방안 E-4).
- `alternatives` 매핑: 구멍 개념의 `present` 쪽도 `count > 0` 이면 패널 행에 「`.then` 체인도 N곳」 부기를 단다 — 사용자가 「왜 두 가지가 있나」를 물을 자리이며 「선택의 왜」(ocul-pm 일지 연동, 01)로 이어진다.
- **「판 만들기」**: 개념을 활성화 → §3.6 으로 첫 노출 Site 선택 → 카드 종류 순서 `point`(pick 있으면) → `meaning` → `blank`(hole 있으면) 중 사전에 있는 첫 것 → 02 §5.5 `role='gap'` 으로 삽입.

### 6.5 대지(unit) 탐지

TS `packages/concepts/units.ts`, 인제스트 파생 때 실행한다. `source='dir'` 만 MVP.

규칙(첫 매치):

1. `features/<x>/**` → 대지 `x`
2. `app/<seg>/**`·`pages/<seg>/**`(Next 라우트 첫 세그먼트, `api` 는 제외) → 대지 `seg`
3. `src/<x>/**`(`x` 가 `lib`·`utils`·`types`·`components/ui` 가 아닐 때) → 대지 `x`
4. 그 밖은 인제스트 파일 ≥ 3 인 2단계 디렉터리 → 디렉터리명

어디에도 안 들면 대지 「기타」.

**기능 대지가 먼저다** (D160). 프론트가 백을 부른 자리(`import_edge.kind='http'` 의 `from`)에서
엣지를 따라간 폐포가 기능 하나이고, 이름은 진입 파일에서 뽑는다(`authService.js` → `auth`).
위의 네 규칙은 **어느 기능에도 안 든 파일만** 받는다 — 둘이 경쟁하지 않고 층을 나눈다.
런타임에 엮이는 것(Spring 필터 체인)은 어느 폐포에도 안 들어 디렉터리 쪽으로 온다.

디렉터리 규칙만으로는 층으로 나눈 리포에서 무너진다 — Spring 은 package-by-layer 라
규칙 3번이 `BACK/src/main/java/…` 를 전부 `main` 하나로 뭉치고, 실측한 리포에서 대지 하나가
백엔드 107파일을 삼켰다.

**`unit_file` 은 파일→대지 N:M 이다** (D160 · 기본키가 `(unit_id, file_id)` 다).
전에 여기 「1:1」이라고 적혀 있었으나 실측이 그것을 반증했다 — 90파일 중 13개가 둘 이상의
기능에 든다(`UserDao` 는 로그인이자 회원정보다). 1:1 로 접는 두 방법을 다 재 봤고 둘 다
정보를 잃는다: 겹치는 것을 빼면 로그인이 18→11 로 깎이고, 가장 작은 폐포에 주면 여덟 기능이
모두 쓰는 `api.js` 가 「이미지」로 간다.

`unit_node` = 대지 파일에 살아 있는 사용처가 있는 T0 개념 + 대지 블록의 대표 개념(T1) + `arch/*` 4개(T2, 후보 커밋 ≥ 3 또는 그래프가 있을 때). `order_idx` 는 02 §6 위상 정렬(대지 개념의 최소 위상). `commit-cluster` 는 MVP 밖.

## 8. 테스트

- **골든**: `fixtures/golden/<lang>/<concept>/<case>.<ext>` + `<case>.expected.json`(`ConceptSite` 배열에서 `siteKey`·`fileId`·`commitId` 제외). Rust 는 같은 파일의 **캡처**를 insta 스냅샷(`crates/parse/tests/snapshots/`)으로 고정하고, Site 비교는 vitest(`pnpm dict:test`)가 캡처 덤프에서 파생해 한다. `UPDATE_GOLDEN=1` 로 갱신. 개념당 양성 3·음성 2 이상. 첫 대상: TS 개념 20개 × projectox 에서 익명화한 줄.
- **쿼리 회귀**: 문법 크레이트를 올릴 때 골든 전체 + `examples` 매치 + 「죽은 패턴」 검사. 문법 업그레이드 PR 은 이 결과를 본문에 붙인다.
- **에러 내성**: 일부러 깨진 파일(중괄호 누락·미완 JSX·Swift 매크로) 픽스처로 `parse-poor` 판정과 Site 폐기가 맞는지.
- **증분/rebase**: 임시 리포를 git2 로 만들어 커밋 → 인제스트 → `reset --hard` 로 rebase 흉내 → `reachable=false` 와 Site id 유지를 검증. 줄을 위로 3줄 밀어도 id 가 같아야 한다(속성 테스트).
- **사전 스냅샷**: 개념마다 고정 가짜 Site 로 모든 템플릿을 렌더한 결과를 `__snapshots__/<id>.md` 에 저장. 문장 변경이 PR diff 에 그대로 보인다.
- **author/필터 단위 테스트**: noreply 형식·mailmap·bot 패턴·bulk 임계·리네임 표.

## 대안과 버린 이유

| 대안 | 버린 이유 |
|---|---|
| LSP(tsserver 등) 로 심볼·타입 추출 | 언어마다 서버 설치·오프라인 불가·초보 환경에서 부팅 실패. 문법 단위엔 tree-sitter 로 충분 |
| 정규식 추출 | 문자열 안의 `?.`, 중첩 괄호, pick 위치가 부정확. T1 채점 폴백에만 남긴다 |
| WASM tree-sitter(웹뷰) | 언어당 wasm 로드·대형 리포 느림 — discussion §B 에서 이미 기각 |
| 커밋 diff 만 파싱(HEAD 스냅샷 없이) | 벌크 초기 커밋의 코드가 빠지고, 여러 번 고친 줄이 중복. diff 는 귀속과 T2 에만 |
| first-parent 워크 | 브랜치 안 기능 커밋이 숨어 T2 정답지 소실 |
| blame 을 1차 패스에 | 대형 리포에서 분 단위 → 배경 2차 패스 |
| 파일 워처 | `node_modules` 이벤트 폭주, 배터리. 세 시점 재스캔으로 충분 |
| 사전을 언어당 단일 YAML | PR 충돌, 4천 줄 리뷰 불가 |
| 쿼리를 YAML 인라인 | 에디터 강조·`tree-sitter query` CLI 시험 불가, 따옴표 이스케이프 지옥 |
| 미지 개념을 사전 `prereq` 만으로 계산 | 같은 줄의 다른 개념을 못 세어 `useState` 줄이 「미지 0」이 된다 → `lineConcepts` 필수 |
| 사전 문장을 LLM 이 실행 시 생성 | 핵심 루프의 LLM 의존 위반(discussion §5) · 검증 불가 진단문 |

## 위험과 완화

| 위험 | 완화 |
|---|---|
| 문법 크레이트 업그레이드로 `.scm` 이 조용히 0건 | 죽은 패턴 검사 + 골든 전체 + `_lang.yaml` 버전 핀 CI 실패 |
| Swift/Dart 커뮤니티 문법이 실코드에서 ERROR 다발 | ERROR 비율 게이트, Site 폐기, 골든 20파일 통과 전 언어 미공개(열린 질문 2) |
| 대형 리포 첫 인제스트 타임아웃 | 스냅샷 1차/blame 2차 분리, 500행 tx 커밋, 취소·이어하기 |
| 사전이 튜토리얼로 변질 | `trace` 의 `{{site.*}}` 참조 강제, 합성 예시엔 예고 필수, 스냅샷 리뷰 |
| 템플릿 값에 사용자 코드가 들어가 XSS | 변수는 기본 이스케이프, HTML 은 사전 문장의 허용 태그만, `|code` 필터가 감싼다 |
| `#match?` 휴리스틱(`^set[A-Z]`) 오탐 | `confidence: heuristic` 저장, 첫 노출에서 후순위, 프레임워크 감지 없으면 비활성 |
| 줄 번호 기반 id 로 학습 기록 유실 | `shape`+`occurrence` id, 속성 테스트 |
| author 오판으로 남의 커밋이 T2 정답지 | 완전 일치만, mailmap, UI 에서 identity 확인 |
| 사용자 코드 전송 | 인제스트는 전부 로컬, 네트워크 호출 0(06 이 검사) |

## 열린 질문 / 결정 요청

1. **숙련도 키** — 보편 개념(`common/*`)에 합산할지, 언어 개념별로 둘지. 제안: 보편 id 에 겹을 쌓고 언어별 「표기 차이」 카드는 언어 id 로 1회성. (02) → 결정: D4 — 겹은 **언어 개념 id**, 전이는 `universal_id` 3겹 기준(02 §6.3).
2. **Dart/Swift 품질 미달 시** — 정규식 폴백으로 T0 를 내는가, 언어를 보류하는가. 제안: 보류하고 앱이 「이 언어는 아직 판이 없습니다」라고 말한다. (사용자) → 결정: 00 §6-2 — 기본 보류.
3. **`react/` 등 프레임워크 네임스페이스** — 문법 사전에 관습을 넣는 것을 허용할지. 제안: 허용하되 `framework:` 필드와 `package.json` 감지로 게이트. (사용자·04) → 결정: 00 §6-3 — 기본 허용.
4. **`.d.ts`·SQL 마이그레이션·테스트 파일(`*.test.ts`)** 포함 여부. 제안: `.d.ts` 제외, 마이그레이션 포함, 테스트 파일 포함하되 `essential` 집계에서 제외. (사용자) → 결정: 00 §6-5.
5. **Rust 가 sqlite 에 직접 쓰는가, IPC 로 TS 에 넘기는가.** 제안: 직접 쓴다(Site 5만 건 직렬화 회피). 테이블 DDL 은 02 가 소유하되 §1.4·§3.3 컬럼을 그대로 받는다. (01·02) → 결정: D1 — 캡처는 Rust 가 직접 쓰고, Site 파생은 TS `packages/concepts`.
6. **사전 별도 배포 채널**(앱 재빌드 없이 갱신). (06) → 결정: 00 §6-6 — MVP 는 번들만.
7. **T2 정답지 core/sec 판정 규칙**을 이 문서의 `added/deleted` 통계로 할지(예: `added ≥ 3 || status==='A'` → core). (04) → 결정: D5 — `core = { status==='A' ∨ additions+deletions ≥ 5 ∨ 유닛 진입점 }`.
